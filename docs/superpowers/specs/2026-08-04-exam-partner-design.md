# Exam Partner — Design Spec

## Problem

Engineering (and other) students are told by teachers to write exam/assignment answers strictly from specific recommended textbooks, but a semester is only 3-4 months and covers ~5 subjects — realistically too little time to read every book and write faithful notes for all of them. Students end up writing answers generated by general-purpose AI (ChatGPT etc.), which don't reflect what the teacher actually recommended.

**Exam Partner** is a chatbot where a student uploads their own study material (books, handwritten notes, slides) as soon as they get it, organized by subject, and later asks questions that are answered *strictly from that uploaded material* — not from the AI's general knowledge, unless the student explicitly asks for a general answer instead.

## Users

Multi-tenant: multiple students will sign up and use the same deployment. Each student's uploaded material and chat history is private to them.

## Platform

Web app, run locally on the developer's machine for now (not deployed to a public host in this phase).

## Material types (launch scope)

- Typed PDFs (textbooks, typed notes, slide exports)
- Word documents (.docx)
- PowerPoint slides (.pptx)
- Handwritten notes as photos/scans (via Gemini vision transcription — see AI Backend)

## Organization

Material is organized **by subject**. A student creates a subject (e.g. "Thermodynamics"), uploads all books/notes for it, and asks questions scoped to that subject. Retrieval never crosses subjects (or users).

## Answering behavior

- Default: answer **only** from the student's uploaded material for the selected subject.
- If the answer isn't found in the material: clearly tell the student "Not found in your uploaded material," with a button to "Get a general AI answer instead."
- If the student takes that option, Gemini answers unrestricted (general knowledge), and the response is clearly labeled as **not** sourced from their material (no citations).
- Every RAG-grounded answer must include citations (filename + page/section) — not optional/best-effort.

## Architecture

- **Backend:** Python + FastAPI — auth, subject/document management, upload pipeline, retrieval, chat.
- **Frontend:** Server-rendered HTML (Jinja2) + HTMX for dynamic interactivity (chat updates, upload status polling). No separate JS build step.
- **Database:** MongoDB Atlas (free M0 cloud tier) — single database for everything: users, subjects, documents metadata, chat history, **and** vector embeddings via Atlas Vector Search. One vector index, filtered per-query by `user_id` + `subject_id`.
- **AI backend:** Gemini API (free tier) — chat generation, text embeddings, and vision-based transcription of handwritten note images (no separate OCR service).
- **Orchestration:** LangChain — `langchain-google-genai` for LLM/embedding calls, `langchain-mongodb` for the Atlas Vector Search store, LangChain document loaders/splitters for chunking, and a retrieval chain enforcing "answer only from retrieved context."
- **Local extraction (pre-LangChain, no API cost):** PyMuPDF/pdfplumber (PDF text), python-docx (Word), python-pptx (PowerPoint).

This means the app needs internet access (Atlas + Gemini are cloud services) even though it runs locally with no public hosting yet.

## Data flow

### Upload flow
1. Student selects a subject, uploads a file.
2. Backend detects file type:
   - PDF/DOCX/PPTX → extract text locally.
   - Image (handwritten note photo/scan) → sent to Gemini vision for transcription.
3. Processing happens as a **background task** (FastAPI `BackgroundTasks`); document status starts `processing`, flips to `ready` or `failed`. No separate job queue needed at this scale.
4. Extracted text is split into chunks (LangChain splitter, ~500-1000 tokens with overlap).
5. Each chunk is embedded (Gemini embeddings) and stored in MongoDB Atlas with a unique `chunk_id`, plus `user_id`, `subject_id`, `document_id`, filename, and page/section metadata.
6. Document record (filename, upload date, status) saved per subject so the student can see what's uploaded.

### Chat flow
1. Student picks a subject, asks a question.
2. Question is embedded (Gemini); MongoDB Atlas Vector Search is queried filtered by **both `user_id` and `subject_id`** — guarantees no cross-user or cross-subject leakage.
3. *(Optional future enhancement, not required for launch)* A reranking step could reorder top vector-search hits before they reach the LLM.
4. LangChain assembles a prompt from retrieved chunks + question + a strict "answer only from this context, and say so clearly if it's not covered" instruction.
5. Gemini generates the answer. If grounded in retrieved content, the response always includes citations (filename + page/section).
6. If not found in context: UI shows "Not found in your uploaded material" + a button to get a general (unrestricted, unsourced) AI answer instead.
7. Every chat entry is saved to MongoDB with a `response_mode` field (`"rag"` or `"general"`), plus citations when `rag`, so history always shows how each answer was produced.

## Components

- **Auth** — signup/login, hashed passwords (bcrypt/passlib), session cookies via FastAPI. Simple email+password; no OAuth/social login at this stage.
- **Subject management** — create/rename/delete subjects; each subject lists its documents and links to its chat.
- **Document management** — upload, list, delete per subject; background processing with status (`processing`/`ready`/`failed`) polled via HTMX.
- **Chat UI** — per-subject conversation view; shows history, citations under RAG answers, and a visible tag for RAG vs. general-AI answers.

## Error handling

- **Bad uploads** (corrupt file, unsupported format, empty extraction) → document marked `failed` with a human-readable reason; student can delete and re-upload.
- **Gemini API errors** (rate limit, timeout) → retry with backoff, then a clear "try again" message — applies to embeddings, chat generation, and vision transcription alike.
- **MongoDB Atlas connectivity issues** → retry briefly, then a clear "service unavailable" error rather than a hang.
- **Empty subject** (chat attempted before any document is `ready`) → chatbot tells the student to upload material first instead of running a pointless empty retrieval.
- **No relevant chunks found** despite documents existing → falls into the standard "not found in your material" flow.

## Testing

- **Unit tests** — text extraction (PDF/DOCX/PPTX parsers), chunking logic, citation formatting — pure functions, no external calls.
- **Integration tests** — full upload→embed→store pipeline and full chat→retrieve→answer pipeline, run against a test MongoDB Atlas cluster/collection, with Gemini calls either minimal-and-real or mocked for CI-style runs.
- **Manual testing** — end-to-end through the actual UI with real PDFs and a handwritten photo, verifying retrieval stays scoped to the right user/subject and citations are accurate.

## Out of scope (this phase)

- Public/cloud deployment (local run only for now).
- Reranking after vector search (flagged as a future enhancement).
- OAuth/social login.
- Semester-level organization on top of subjects.
- Mobile app.
